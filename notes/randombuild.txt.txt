FUSE Glance — your inbox in thirty seconds, on your face. An Even Hub app for the Even Realities G2, built on @evenrealities/even_hub_sdk 0.0.16. Main track: 01 · Messaging & News (Telegram) — also entering the Best Telegram integration special prize.

The problem
A message arrives while your hands are busy and your phone is in a pocket. Taking it out costs you the moment: unlock, open the app, read, think of a reply, type it. On a pair of glasses the fix is not "put the phone screen on your face" — it is to show one thing and offer one action, so the decision costs a single tap.

Who it is for
Anyone who wears G2 at work or on the move and has to answer short messages without breaking what they are doing: in a meeting, on a bike, carrying things, mid-conversation. They do not want an inbox on their face. They want the one message that is waiting, the gist of it, and a reply they can accept with a tap.

How it works (in the repo today)
Two screens, one control surface, one decision.

Board screen. A 5x5 Lights Out board derived from the UTC date, so every user gets the same board and it cannot be pre-solved. Par is the exact minimum, not an estimate: solveMinimal (src/shared/puzzle.ts) enumerates all 32 first-row press patterns, chases the lights down, and keeps the shortest — valid because each reachable state has exactly one first-row pattern. The test suite cross-checks it with an independent solver that does real Gaussian elimination over GF(2) and asserts the two agree, plus that replaying that minimal solution clears the board, for 365 consecutive days (tests/puzzle.test.ts: independentMinimal, 365-iteration loop).
Glance coach. A long-press turns the same display into a messaging card: who pinged, what they said, and a reply drafted for you. One tap accepts and sends (src/even/telegram.ts — pure routing: digest → draft → send receipt; src/client/main.ts — the two screens).
One control surface. The G2 has a single touch surface and the R1 ring mirrors it. Five SDK event types — SCROLL_TOP_EVENT, SCROLL_BOTTOM_EVENT, CLICK_EVENT, DOUBLE_CLICK_EVENT, LONG_PRESS_EVENT — collapse into four actions (up / down / tap / long-press) in one switch (src/even/hub.ts: toInput), so preview, simulator and glasses share one input model.
The send path is real, not a mock. Replies leave through our own server, which holds the bot token; the WebView never sees a credential (src/even/bot.ts, plus /api/tg/status, /api/tg/updates and /api/tg/send proxies in src/server/index.ts). Without a token the app runs on bundled demo chats and the header says DEMO, so the demo never depends on a secret; with TELEGRAM_BOT_TOKEN set the header says TG LIVE and the coach shows real chats.
How the display is driven (technical execution)
Even Hub runs a WebView, but the G2 shows text containers, not HTML. src/even/layout.ts is the single source of truth: app state becomes three strings (header / body / status), and those same strings are painted in the preview and pushed to the display through CreateStartUpPageContainer / TextContainerUpgrade (src/even/containers.ts). There is no second rendering path to drift.

Every firmware constraint is pinned by a test rather than by hope:

Constraint	Enforced in
Exactly one container sets isEventCapture: 1	src/even/containers.ts; test asserts 1 of 3
zOrderIndex on all containers or none, unique values	src/even/containers.ts; test asserts uniqueness
Text ≤ 999 UTF-8 bytes per container	layout.ts: MAX_CONTAINER_BYTES; test measures bytes
≤ 12 containers per page	3 are used
576x288 per eye, ~42 monospace chars per line	layout.ts: MAX_LINE_CHARS, derived from font metrics
The status line drops whole fields by priority (layout.ts: fitFields) instead of truncating a number in half — COACH .. is worse than no coach count at all.

Verification — every claim above is one command
bash scripts/gate.sh runs the whole gate in one shot: typecheck, unit tests, build, a real headless-Chromium render at 576x288, a pixel-level audit, the .ehpk stamp, video checks and a rebuild of the public demo origin. Latest full run: 8/8 stages PASS, 2026-11-21T13:53:35Z.

tsc clean on app, server and tests; 26/26 unit tests pass.
Real Chromium at 576x288: 14/14 checks green — 25 cells as 5 rows of five on five distinct row tops and five aligned column lefts, three bands, coach opened, draft produced, reply sent (sentCount 1), board solved in exactly par taps (7/7), body inside the 999-byte budget, zero page errors.
scripts/pixel_audit.py PASS: the 25 DOM-reported rectangles are re-checked against the actual pixels, and every lit/dark cell matches the server's board for the day. The pixel audit exists because the DOM can lie — an earlier build reported 25 cells while CSS had wrapped each row into six, and a DOM-only check called it green. The audit is itself tested against a blank canvas, a tampered board and the wrong screenshot before it is trusted.
evenhub pack app.json ./dist --sdk-ver 0.0.16 stamps fuse-glance.ehpk. The property that matters is determinism, not a particular size: two consecutive runs over the same dist produce a byte-identical archive, because the CLI is pinned in devDependencies and the lockfile is committed. At the commit this description describes (4dc5a0c) the artifact is 43,450 bytes, sha256 7022d96a516c33066f401df5100186f923683240e1704d506fc9006f5ed6f691 — which is exactly the file bash scripts/gate.sh emits, so you can compare your own build against it; any later commit that changes the bundle will move both numbers together. The archive is deliberately not committed (*.ehpk is in .gitignore), so the README builds it rather than shipping it.
The 576x288 display, and what it costs
The whole UI is three text containers — header, body, status — on a 576x288 monochrome panel, about 42 monospace characters per line and 8 body lines. That budget is the design constraint, not a limitation to apologise for: it forces one decision per screen. Grouping is done with # blocks plus a cursor row marker, so you always know what a tap will flip; the coach card fits sender, message and draft inside those same three containers.

Run it in two commands
npm install
npm run serve     # typecheck + build, serves the preview and the API on :5199
Open https://fuse-glance.surge.sh in a 576x288 window and the frame renders 1:1 — a judge needs no glasses and no simulator to see the app work. Keys: up/down move, Enter taps, Tab switches screen. Live Telegram mode:

TELEGRAM_BOT_TOKEN=<token> TELEGRAM_CHAT_ID=<chat> npm run serve
Business potential and safety
Path into Even Hub. The app is already packaged as an .ehpk with an app.json manifest (package_id, min_sdk_version 0.0.16, one entrypoint) and exactly one network permission, whitelisted to https://api.telegram.org — the same-origin backend call needs no entry. What remains for a store listing is the listing itself, not engineering.
What it becomes with users. The daily board is the retention hook (one board a day, a streak, a shareable result); the coach is the daily utility. Both screens exist today and share one engine.
Careful with data and money. No account is created inside the app, no analytics, no third-party script, no wallet. The Telegram token lives on the server and never in the WebView, and the app can reach exactly one host.
Licence. MIT. Source, README and the full verification story are in the repo.
Honest scope, including voice
Tap-first, not voice-first. The SDK we build on (@evenrealities/even_hub_sdk 0.0.16) exposes an audio channel — audioEvent with audioPcm frames and an AudioInputSource of glasses or phone — but this build does not subscribe to it: there is no microphone code in src/, and no dictation. The reply itself is drafted for you rather than spoken, and accepting it is one tap; wiring the SDK's audio frames to a spoken reply on the same coach card is the next step, not a shipped feature. Nothing in this submission depends on something that is not in the repo: every claim above names the file or the command that proves it.

Built before this hackathon (disclosure)
The rules ask for "something new, or something clearly better". This app is built on an earlier project of ours, fuse — a daily puzzle + coach web app for a phone browser. Reused unchanged: src/shared/puzzle.ts (board generator and GF(2) exact solver — the game's engine, not written during the hackathon). New for this hackathon: the whole Even Hub application — src/even/ (layout, containers, bridge, Telegram router, bot client), src/client/ (two-screen UI and its four-action model), src/server/ (preview, score replay, Telegram proxy), app.json, the packaging, and the app-level tests. The phone version had no text containers, no byte budget, no z-order or event-capture rules, and no coach-to-send round trip.

Feature requests — five things the Even Hub SDK is missing
The rules invite up to five feature requests. These are the ones we actually hit while building, each with the line of our code that works around it:

No text metrics. The typings expose no measure-text API, so how many characters fit in a container is a guess unless you reproduce the font metrics yourself. We did: layout.ts keeps CHAR_ADVANCE_EM = 0.6 and derives MAX_LINE_CHARS = 42 from the 576 px width.
No word wrap, and no styled spans. A page is built from textObject entries (PB Text_Object) typed as TextContainerProperty: content plus one textColor brightness (0-4). The typings carry no wrap helper and no bold / italic / font-size field at all — grep bold, italic, fontSize over index.d.ts returns 0 — so the app wraps every line itself and any emphasis inside a message is flattened.
No transcript on the audio channel. AudioEvent hands you audioPcm frames and their source, but not text — so a spoken reply means running our own recogniser. That is exactly why this build is tap-first.
Only one container may capture events, and nothing enforces it. isEventCapture is documented as a flag but not as a mutual-exclusion rule; two containers set to 1 silently steal input. We pin it with a test instead of trusting it.
No read-back of what the display is showing. There is no "get current page" call, so the app must keep its own mirror of the screen (layout.ts) and treat that as the truth — any drift is invisible from the SDK side.
The reply chain, recorded: card → draft → SENT
Read and write is the criterion a text description cannot win. This is the round trip itself, captured frame by frame from the Even Hub desktop simulator — the environment the submission rules accept for the demo video. The app runs in the simulator's WebView and renders to the simulated 576×288 monochrome lens; the inputs are real events into the app's own four-action model (Tab = long press, Enter = click, ArrowDown = down — src/client/main.ts), not a scripted animation.

The card is read. One long press leaves the board and lands on the top card of the unread carousel — CARD 1/3, the first of three channels: who pinged and what they asked, inside the lens's three-container budget. Glance card — one long press, unread group, sender and message on the lens
One tap drafts. No dictation, no keyboard: composeReply() (src/even/telegram.ts) reads the pending question and writes a reply that fits one line of the lens. Draft — one tap composes the reply on the card
A second tap sends, and the lens says SENT. The receipt carries the exact string that was handed to the send path, so the confirmation cannot disagree with what was sent. SENT — the receipt carries the delivered text
And it repeats on the next card. ArrowDown moves on; the unread total on the status line is unchanged, because the reply did not mark anything read behind your back. SENT on the second card — same one-tap chain
The reply chain itself, recorded as a 61 s mp4 cut (no cuts, narrated): https://dh2477-evenhub.surge.sh/fuse-glance-coach-chain.mp4 The demo video for this submission (64 s, Vimeo — the shipped build in the Even Hub simulator, daily 5x5 board and lens counter): https://vimeo.com/1249183269 The page, if you would rather step through the five stills: https://dh2477-evenhub.surge.sh/coach.html

What this shows and what it does not: it shows the lens carrying the incoming card, the composed draft and the SENT receipt, and that one long press plus two taps is the entire cost of turning an unread message into a delivered reply. It is the simulator, not a G2 in someone's hand. The chat content is invented on purpose (DEMO_CHANNELS in src/even/telegram.ts) so no real conversation is published; with a bot token the same code path posts the identical string to Telegram and logs the returned message_id (src/even/bot.ts). The narration is synthesised and each line starts at the moment its state reached the lens. The numbers on screen come from a public endpoint, not a mock
Replaying the Telegram path end to end needs a bot token. The other half of this repository needs none: FUSE Tick (the same repo, submitted to Track 02 of this hackathon) renders live Hyperliquid mainnet state from a keyless public endpoint.

POST https://api.hyperliquid.xyz/info with {"type":"clearinghouseState","user":"0x51a04fc0b977d4d453c60f70d43119a3023a3543"}

That 40-hex account is the one the deployed bundle actually reads (__FUSE_ADDRESS fallback in src/client/main.js), and at 2026-11-23T03:08:24Z it held 4 open positions — BTC +56.83 @ 20x, ETH +1,901.24 @ 20x, HYPE −2,869.61 @ 10x, XMR −6,064.40 @ 5x — against 235 perp markets. That table is a frozen reading, not a promise about the present: positions move, so asking the same endpoint later returns different numbers, and the address plus the request shape are what stay fixed. No screenshot, no recording, no mock stands between the lens and the chain. Every fill the venue reports carries its own transaction hash, and userFillsByTime returns them verbatim. Best Telegram integration — what is actually built
The special prize asks for "the best use of Telegram (accounts, bots, channels or Mini Apps) on G2". What this app uses is the Bot API with channels, on-device for input and off-device for delivery:

Special-prize criterion	Where it lives	Test that pins it
bots	src/even/bot.ts — fetchUpdates() / sendMessage(); card text from digestLine() / composeReply() / sentLine()	bot updates fold into one card, newest first, and skip textless messages
channels	DEMO_CHANNELS (three bundled) and TELEGRAM_CHAT_ID for the live one (read at src/server/index.ts)	a channel with no text-bearing updates yields null, not an empty card
on G2, read and write	three text bands (src/even/containers.ts); approving a draft sends it	the page has exactly one event-capture container and unique z-order
Delivery is backend-first with a direct fallback: sendMessage() posts through /api/tg/send, and only if no usable backend answers does it call sendMessage on the Bot API itself. The token therefore never reaches the WebView. With no token the app runs on the bundled channels and the header prints DEMO.
